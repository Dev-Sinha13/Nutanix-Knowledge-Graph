# ENG-910344 — RPC resolvers (identity enrich / resolve)

Back: [IMPACT index](README.md)  
Shipped path: [iam-themis #1535](https://github.com/nutanix-core/iam-themis/pull/1535) (merged 2026-06-04, `de3b0638`)  
Follow-on: [ENG-910347](ENG-910347.md)

---

## 1. The problem

Access Control Policies name people and groups as **UUIDs**. Those IDs are valid only on the **source** cluster’s AuthN. After lattice copy to another PC (especially **brownfield** join), the same human often has a **different** UUID. Copying the ACP verbatim authorizes the **wrong principals** — or nobody.

Greenfield-to-greenfield can no-op (IDs already match). Real Global IAM customers are brownfield. There was no stable cross-cluster identity on the ACP row, and persisting enricher metadata on the AP would have polluted AuthZ storage with AuthN connector details.

---

## 2. How it was solved

Two gRPC services (`iam-utils/identityresolver`, servers in `iam-user-authn`):

| Service | Where it runs | Job |
| --- | --- | --- |
| **IdentityEnricher** | NC (producer) | UUID → `{connectorType, connectorIdentifier, userIdentifier, entityType}` |
| **IdentityResolver** | every replica | those properties → **local** UUID; if missing, **deterministic v5 fallback** |

Canonical key: `connectorType|connectorIdentifier|userIdentifier|entityType`. Batch window `[1,50]`.

**Enrich on the producing cluster, resolve on the consuming cluster.** Enrichment rides the wire **in transit only** — never stored on the ACP row.

#1535 wired this into v4 ACP create/update and Lattice **ApplyChange**. Design doc: `iam-themis/docs/global-acp-authn-uuid-resolution.md`.

It did **not** wire bulk shard copy — that remaining hole is ENG-910347.

---

## 3. Impact

- **Correct authorization after federation** for incremental create/update/sync — the core of global ACPs.
- **v5 fallback** keeps a stable UUID if the user is not yet present on the learner, so a later AuthN create can match.
- **Reviewed vocabulary and batching** (Aditya: “AP” not “ACP”; Praveen: batch-size perf) became the template 910347 had to follow, not fork.

## 5. Technologies and skills

- gRPC, protobuf (`identity_resolver.proto`), Go.
- IAM AuthN identity model (connectors, not raw UUIDs).
- Lattice ApplyChange vs REST.
- UUID v5 as a deterministic placeholder.
- Design-doc discipline for global-IAM/lattice changes.

---

## 6. Significant technical difficulties

**UUID locality vs global grants.** There is no “same UUID everywhere” in brownfield. Approach: **property-based identity** (connector tuple) instead of copying IDs.

**Must not persist enrichment.** If connector blobs land on the AP row, AuthZ storage becomes a second AuthN database and older peers choke. Approach: **sidecar map on the change payload**, nil after resolve.

**e2e on a single AuthN.** Even #1535’s tavern used identical UUIDs on leader and learner, so it proved wiring more than rewrite. Approach: accept that **divergent-UUID coverage lives in unit tests / a true brownfield rig**; do not claim tavern proved the transform.

**Naming / AssociationResolver confusion.** “Resolver RPCs” in the ticket is IdentityEnricher/IdentityResolver, **not** enforcement `AssociationResolver`. Approach: confirm against `identity_resolver.proto` before touching the wrong package (910347 D0).
