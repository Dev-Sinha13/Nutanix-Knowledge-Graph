# ENG-910344 — RPC resolvers (identity enrich / resolve)

**Company impact:** This is the **federated-identity model** for global Access Control Policies. User and group UUIDs are cluster-local. Copying them verbatim to another cluster points the ACP at the **wrong principals** (or at nobody). Enrich-on-source / resolve-on-target is how a global grant still means “this AD/SAML human” after replication.

Back: [IMPACT index](README.md)

ENG-910344 is the parent “RPC resolvers” effort. The **incremental** path shipped in **merged** iam-themis [PR #1535](https://github.com/nutanix-core/iam-themis/pull/1535) (2026-06-04, `de3b0638`). ENG-910347 extends the same model to **bulk shard copy**.

---

## The customer / product problem

An ACP stores `UserList` / `UserGroupList` / `Identities` as UUIDs. Those IDs are valid on the **source** cluster’s AuthN. On a **target** PC, the same person often has a **different** UUID (brownfield join). Greenfield-to-greenfield can no-op (IDs already match). Real customers are brownfield.

Without enrich/resolve:

- A global ACP copied to a new PC authorizes the wrong UUIDs.
- Authorize checks on the learner pass or fail for the wrong people.
- There is no stable cross-cluster key.

---

## The model (what #1535 shipped)

Two gRPC services (`iam-utils/identityresolver`, servers in `iam-user-authn`):

| Service | Where | Job |
| --- | --- | --- |
| **IdentityEnricher** | NC (producer) | UUID → `{connectorType, connectorIdentifier, userIdentifier, entityType}` |
| **IdentityResolver** | every replica | those properties → **local** UUID; if missing, **deterministic v5 fallback** so references stay stable |

Canonical key: `connectorType|connectorIdentifier|userIdentifier|entityType`. Batch window `[1,50]`; Themis batches at `identityBatchSize`.

**Enrich on the producing (leader/NC) side, resolve on the consuming (follower) side.** Enrichment metadata is **transit-only** — never persisted on the ACP row.

#1535 wired this into:

- v4 ACP create/update (`v4_access_policy.go`)
- Lattice **ApplyChange** (`apply_change.go`)

Design doc: `iam-themis/docs/global-acp-authn-uuid-resolution.md`.

It did **not** wire `FetchShardData` / `WriteShardData`. That gap is ENG-910347.

## Why this is company-visible

1. **Correct authorization after federation** — the point of Global IAM ACPs.
2. **v5 fallback** — a user not yet present on the learner still gets a **stable** UUID so later AuthN create can match.
3. **Reviewed vocabulary** — reviewers required “AP” not “ACP” in naming; batch-size perf was flagged (Praveen) and carried into 910347 D5.
