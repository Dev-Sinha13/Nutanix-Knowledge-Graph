# ENG-949861 — Authoring-scope mutation guard

Back: [IMPACT index](README.md) · Engineering notes: [inbox index](../inbox/ENG-949861%20-%20Authoring%20scope%20mutation%20guard/00%20-%20Index.md)

---

## 1. The problem

ENG-915519 stored **origin** on global Roles and ACPs. It did not **enforce** it.

On Prism Central, a local admin or script could still attempt PUT/DELETE on an object that Nutanix Central authored. Even where a blanket check already rejected “globals from the API on PC,” the error was HTTP **400** with a **product-limitation** message (`"Global ... are only allowed for NC products"`). That is the wrong story for customers and for GA: it sounds like “PC cannot do globals,” not “this object is owned by Central.”

If that blanket check is later **relaxed** for Global IAM GA, NC-authored rows on PC become writable unless a **field-keyed** guard exists.

Requirement (Jira was 503 that session; taken from the user + Kronos design): block PUT/DELETE when the request runs on **PC** and stored `authoringScope` is **NC**; 403; message that the entity is managed by Nutanix Central; **API handler only** so Lattice sync still works.

---

## 2. How it was solved

A shared helper `IsAuthoringScopeMutationBlocked(authoringScope)` = `IsPCProduct() && authoringScope == "NC"`, placed in the four v4 update/delete handlers **after fetch, before `AllowOperation`**.

- HTTP **403** + existing `ModificationNotAuthorized` + constant message about NC management.
- **Directional** (NC→PC only), matching replication.
- **Not** in persistence — `ApplyChange` must keep updating PC copies.
- Scalar compare (`== "NC"`), not “array contains NC.”

v1/proxy not covered (v4-only, same as ENG-910350).

---

## 3. Impact

- **Customer-facing ownership:** PC operators see a 403 that names Nutanix Central, not a vague global-on-PC 400.
- **GA-proofing:** if `AllowOperation`’s blanket PC block is relaxed, NC-authored objects stay read-only on PC.
- **Federation preserved:** lattice can still apply NC changes. A storage-layer block would freeze PC copies.

---

## 4. How it was done

1. Read ENG-915519 (scalar lock) and ENG-910350 (handler-layer validator pattern).
2. **Audit existing gates** before writing a new block — found `AllowOperation` already rejects API globals on PC, and `authoringScope=="NC"` is equivalent to “global stamped on NC” under current create rules.
3. Therefore a naive “add a block” would be **dead code**. Redesign: run the new guard **first** for the better status/message and for durability if the blanket gate changes.
4. New branch/worktree **off ENG-915519**, because `authoringScope` did not exist on Themis main.
5. Wire four handlers; add helper tests (5 cases) and handler tests for **all four** paths (AP-update added in session 2 by mirroring a proven `IsGlobal` template — originally skipped as “fragile,” reversed when the template proved the chain is reachable).
6. Verification: gofmt/build/vet/test; existing PC global-block tests still pass because mocks leave `AuthoringScope` empty.
7. Tavern: **not** added — the harness only flips PC→NC, not NC→PC (see difficulties).
8. Not committed in the notes (pending 915519 merge + Jira confirmation of error code).

## 6. Significant technical difficulties

**Dead-code trap.** The described block already existed via `AllowOperation` + the stamp rules. Approach: implement a **non-redundant** guard (403 + NC message + future-proof), not a second copy of the 400.

**Jira/brief said array; code said scalar.** ENG-915519 had flipped on 2026-06-01. “Contains NC” would have been the wrong check. Approach: **read the locked spec and storage type before writing**; document the correction in the ticket note.

**Where to enforce.** Persistence would break Lattice. Approach: same as 910350 — **handler after fetch**, only for API callers.

**Tavern cannot exercise NC-on-PC.** `setup_global_iam_product` flips PC→NC only. A real e2e needs reverse flip, extra pod restarts, and teardown that can still delete despite the guard. Approach: four Go handler tests as the contract; tavern deferred as **test-infra**, not as skipped coverage pretending to exist.

Depends on unmerged ENG-915519. Status 2026-07-09: implemented, gates green, **not committed**.
