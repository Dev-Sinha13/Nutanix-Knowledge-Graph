# ENG-949861 — Authoring-scope mutation guard

**Company impact:** On Prism Central, a user cannot update or delete a Role or Authorization Policy that was **authored on Nutanix Central**. The API returns **403** with an ownership message. Lattice sync can still mutate those rows, so federation does not freeze.

## The customer / product problem

ENG-915519 stored origin but did not **enforce** it. Without a guard:

- A PC operator (or a confused script) can PUT/DELETE an NC-authored global Role/ACP.
- Even if a blanket “globals only on NC” check exists, the error looks like a **product limitation** (HTTP 400, “Global … only allowed for NC products”) rather than **ownership**.
- If that blanket check is later relaxed for Global IAM GA, NC-authored objects on PC become writable unless a **durable, field-keyed** guard exists.

Requirement (Jira 503 that session; taken from user + Kronos design):

- Block PUT/DELETE when **both** (1) request runs on **PC** and (2) stored `authoringScope` is **NC**.
- Scope: Roles and ACPs (the types that carry `authoringScope`).
- Enforce at the **API handler**, not persistence — Lattice `ApplyChange` must keep working.
- Message: `"This entity is managed by Nutanix Central and cannot be modified or deleted locally on Prism Central."`

---

## The finding that changed the implementation

`AllowOperation(isGlobal, caller)` already returns false on PC for `isGlobal && caller==CallerAPI`. All six create/update/delete handlers already reject globals from the API on PC.

And `authoringScope=="NC"` is equivalent to “this global was stamped on NC” (create on PC stamps `"PC"`; global↔local conversion rejected; globals cannot be created on PC). So a naive new “block NC-on-PC” would have been **dead code** today.

**Resolution:** place `IsAuthoringScopeMutationBlocked` **before** `AllowOperation`:

- Same cases get the **spec’d 403 + NC-managed message** instead of a misleading 400.
- If `AllowOperation` is later relaxed, this guard **still** keeps NC-authored entities read-only on PC.
- Other cases fall through unchanged.

Also: the brief said “array contains NC.” ENG-915519 had already flipped to a **scalar**. The implementation is `authoringScope == "NC"` && `productutil.IsPCProduct()`. An agent that only read Jira would have shipped the wrong check.

---

## What shipped (code, not yet a PR in the notes)

Helper: `util.IsAuthoringScopeMutationBlocked` next to `ComputeAuthoringScope`.

Wired in four v4 paths, after fetch, before `AllowOperation`:

- `DeleteRoleById` / `UpdateRoleById`
- `UpdateAuthorizationPolicyById` / `DeleteAuthorizationPolicyById`

Error: existing `ModificationNotAuthorized` + HTTP 403 (authorization semantics, not “bad request”).

Directional: **NC→PC only**, matching Kronos replication. A PC-authored global is not blocked.

v1/proxy **not** covered (v4-only, same as ENG-910350 D5).

## Tests

- Helper: 5 cases.
- Handler: all **four** guarded paths (`NCAuthoredOnPC`) — AP-update test added after finding a proven template (`TestUpdateAuthorizationPolicyById_IsGlobal_OperationNotAllowed`).
- Existing PC global-block tests still pass: their mocks leave `AuthoringScope` empty so the new guard does not trip.
- **Tavern deferred:** the guard only fires for an **NC-authored entity present on PC**. The tavern helper only flips PC→NC, not back. Exercising this needs a reverse product-flip, extra pod restarts, and teardown that can still delete under the guard. Documented, not faked.

## Why this is company-visible

1. **Support / UX:** “managed by Nutanix Central” is the sentence a customer should see, not a generic global-on-PC 400.
2. **GA-proofing:** the field-keyed guard survives a future relaxation of the blanket PC block.
3. **Federation safety:** handler-layer (not storage) so Lattice can still apply NC changes onto PC.

Depends on unmerged ENG-915519 (`authoringScope` does not exist on Themis main in these notes).
