# ENG-953364 — Run-once completion contract (role `products` brownfield migration)

Back: [IMPACT index](README.md) · Field: [ENG-932537](ENG-932537.md) · Follow-on: [ENG-956163](ENG-956163.md)  
Evidence: `iam-themis/.notes/PRODUCTS_FIELD_CONTEXT.md`

---

## 1. The problem

ENG-932537 adds `products` for **new** Entities and Roles. Brownfield clusters already have Roles. Those rows need a **one-shot migration** that recomputes role products from accessible entities **for every tenant**, then records **global completion**.

IAM Bootstrap is the coordinator; Themis workers are tenant-scoped.

The dangerous implementation is: tenant list returns **zero** objects (AuthN not ready, wrong cluster, pagination assumed but the API is unpaginated, empty enumeration treated as success) → coordinator sets **complete** → no worker ever runs → NC filters on `products` as if the fleet were migrated → data is still empty.

“Success on zero work” looks green in pipelines and is wrong in production.

---

## 2. How it was solved

A **run-once completion contract**:

- Global coordinator owns fan-out and the **final** completion bit.
- Each tenant worker processes **exactly one** tenant and reports success/failure.
- Completion is written **only after every tenant succeeds**.
- An **empty tenant list is retryable and leaves completion unset** — because **this** migration must fan out. (Other APIs may legitimately return zero objects; that rule is **not** universal.)

Pagination is verified from the **live** AuthN list endpoint (current v1 tenant list is unpaginated — a fact, not a forever assumption).

---

## 3. Impact

- Upgrades cannot mark “products migration done” while brownfield roles still have empty `product_list`.
- NC topology filters stay honest on existing fleets, not only on clean seed.
- Support does not debug a flag that says done and a database that says empty.

---

## 4. How it was done

Specified as coordinator vs worker responsibilities; encoded in Bootstrap completion logic and Themis tenant-scoped work; tested as part of the products migration suite (see also 956163 tavern: migrate then prove completion semantics). Documented in the cross-issue IAM notebook so later tickets do not copy Lattice `WalTenantID` tablet-copy assumptions onto REST batches.

---

## 5. Technologies and skills

- iam-bootstrap orchestration, iam-themis storage/handlers, AuthN tenant list, Postgres role `product_list`.
- Distributed “exactly once fan-out then a durable flag” design — distinct from in-memory feature flags (ENG-924709).

---

## 6. Significant technical difficulties

**Empty list looks like success.** Approach: for this operation, empty enumeration **must not** complete; retry.

**Pagination folklore.** Assuming AuthN list is paginated (or the opposite) silently drops tenants. Approach: **read the actual endpoint**; record “unpaginated today” as an implementation fact.

**Wrong analogy from Lattice.** Tablet copy is tenant-bounded by `WalTenantID`. Approach: do not reuse that bound for arbitrary bootstrap/REST batches.

This contract is **feature-specific**. Copying “empty ≠ complete” onto APIs that should accept zero objects would be equally wrong.
