# ENG-910350 — Global ACPs only on externally managed identities

**Company impact:** You cannot create or update a **global** Access Control Policy that names a **local user** or **service account**. Those identities are cluster-scoped. Replicating a grant to them is meaningless on other clusters and a **data-integrity hazard**. This is an authoring-side guardrail on NC (the leader).

## The customer / product problem

Global ACPs are lattice-replicated. ENG-910347’s enrich/resolve model only works for identities that have **connector properties** (SAML/LDAP/external IDP, NC-propagated groups). A LOCAL user or SERVICE_ACCOUNT has **no stable cross-cluster identity**. A “global” ACP that grants to `local-admin` on NC does not grant to a corresponding human on PC — it grants to a UUID that does not federate.

Without this guard, NC would happily author a global policy that is **wrong everywhere it replicates**.

`isGlobal` already existed. **No new public field.** Themis-only.

---

## What shipped

Validator `validateGlobalACPExternalIdentities` in the v4 ACP handler, **after** `CheckIfGlobalChangeAllowed` and **before** enrich/propose to lattice:

- Dedupes lists; skips `""` and `"*"` (dynamic match-any — left to per-cluster runtime).
- Users: `GetUserById`; allow `{SAML, LDAP, EXTERNAL, PROPAGATED}`; deny LOCAL, SERVICE_ACCOUNT, UNKNOWN, REDACTED, nil.
- Groups: `GetUserGroupById`; allow `{SAML, LDAP, PROPAGATED}`.
- 404 → request validation “does not exist”; other AuthN errors → fail-closed `InternalError` (same posture as 910347 D3).
- Reuses `v4_role_membership_validator.go` error mapper and IAMAuthn SDK v17 (not iam-server-codegen).

OIDC is represented as **SAML** in the v4 enum — there is no OIDC user type.

**Bootstrap audit:** seed ACPs never set `IsGlobal`, so defaults are local. Guard cannot break bootstrap. No bootstrap change.

**Tavern:** four stages on `test_global_role_acp_crud.tavern.yaml` — create LOCAL user, assert global ACP **create** referencing it fails (400/IAM-20027), assert **update** adding it beside an AD user fails, cleanup. LDAP allow path already covered by existing combo stages. ASCII-only; 65 stages parse. Not yet run on a cluster in the notes.

## Why this is company-visible

1. **Prevents shipping federated grants that cannot federate.**
2. **Fail-closed** if AuthN is down — better than authoring a global ACP that later resolves wrong.
3. **Honest open product questions** still listed: allow `USERTYPE_EXTERNAL` (gmail-type)? allow wildcard `user:*` on global ACPs? **v1/proxy hole** — v1 `serveAccessPolicyPOST` does **not** call `AllowOperation`, `CheckIfGlobalChangeAllowed`, or this validator. If v1 global create is reachable, the guardrail is bypassed (flagged because 932537 treated v1+/proxy as real write paths).
