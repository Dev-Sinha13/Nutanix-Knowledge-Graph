# ENG-910350 — Global ACPs only on externally managed identities

Back: [IMPACT index](README.md) · [inbox](../inbox/ENG-910350%20-%20Global%20ACP%20external%20identities/00%20-%20Index.md)

---

## 1. The problem

Global ACPs replicate across clusters. ENG-910347’s enrich/resolve model only works for identities that have **connector properties** (SAML, LDAP, external IDP, NC-propagated groups). A **LOCAL** user or **service account** has **no stable cross-cluster identity**.

Authoring a “global” ACP that grants to `local-admin` on NC therefore:

- does not grant to a corresponding human on PC
- replicates a UUID that cannot federate
- is a **data-integrity** bug that looks like a successful create

`isGlobal` already existed. No new public field was required. The hole was **authoring-side validation**.

---

## 2. How it was solved

`validateGlobalACPExternalIdentities` on the v4 ACP **create and update** global branches, **after** `CheckIfGlobalChangeAllowed` and **before** enrich/propose:

- **Allow-set** (fail-closed), not a deny-list: users `{SAML, LDAP, EXTERNAL, PROPAGATED}`; groups `{SAML, LDAP, PROPAGATED}`. LOCAL, SERVICE_ACCOUNT, UNKNOWN, REDACTED, nil → reject.
- Lookup via **IAMAuthn SDK** `GetUserById` / `GetUserGroupById` (same pattern as `v4_role_membership_validator.go`), **not** the IdentityEnricher’s `connectorType` (enrich runs later; connector semantics are less explicit than `UserType`).
- Skip `""` and `"*"` (dynamic match-any).
- 404 → validation error; other AuthN errors → **fail-closed** InternalError.
- No new feature flag — inherent in the existing global-sync gate (NC + lattice enabled).

OIDC is **SAML** in the v4 enum. Bootstrap seeds never set `IsGlobal` — no bootstrap change.

---

## 3. Impact

- NC cannot publish a federated grant that **cannot federate**.
- Fail-closed if AuthN is down rather than authoring a global ACP that later resolves wrong.
- Pattern reused by ENG-949861: **handler-layer guard, not persistence**.

## 6. Significant technical difficulties

**Allow-set vs deny-list.** Ticket said reject LOCAL + SA. Unknown/nil types must not slip through. Approach: permit only known external types; `EXTERNAL` and `PROPAGATED` treated as external (product can drop `EXTERNAL` later by editing two maps).

**Wrong oracle.** Enricher’s `connectorType` is adjacent but runs **after** the fail-fast point and is a different enum. Approach: **explicit UserType/GroupType lookup**, reuse membership-validator error mapper.

**Shared generated SDK client is not goroutine-safe.** `go test -race` showed the generated client mutating request/logger state. Approach: do not fan-out `GetUserById` on one shared client without locking or per-call clients; validation is sequential per distinct UUID (lists are small). Recorded as a cross-ticket IAM lesson.

**v1/proxy hole.** `serveAccessPolicyPOST` does **not** call `AllowOperation`, `CheckIfGlobalChangeAllowed`, or this validator, and does not propose to lattice. If v1 global create is reachable, the guardrail is bypassed. Approach: v4-only for this ticket (D5) because global authoring is a v4 concern; **explicitly flag** the hole because 932537 treated v1+/proxy as real write paths — do not pretend it does not exist.

**Wildcard `user:*`.** Skipped as dynamic. A global grant-to-all is still possible. Approach: document as an open product question, not silent deny.
