# ENG-910347 — Resolver RPCs for shard read/write (ACP)

Back: [IMPACT index](README.md) · [inbox](../inbox/ENG-910347%20-%20Resolver%20Shard%20ACP/00%20-%20Index.md) · Jira: [ENG-910347](https://jira.nutanix.com/browse/ENG-910347)

---

## 1. The problem

#1535 (ENG-910344) rewrote ACP identities on **create/update and ApplyChange**. A newly joined PC does not get its initial global ACP set that way. It gets a **bulk shard copy**: `FetchShardData` on the leader, `WriteShardData` on the follower.

`shard_data.go` on master had **zero** enrich/resolve calls. Day-0 bootstrap therefore **persisted source-cluster UUIDs**. Incremental sync later might fix them; until then, authorize on the learner was wrong. That is a **join-day** product bug.

Themis-only: internal lattice RPC, proto already vendored.

---

## 2. How it was solved

Faithful extension of #1535, no forked algorithm:

1. Transit-only `APEnrichedIdentities` on `shardDataBatch` (`omitempty`). **Per-AP map** because a batch holds many APs (ApplyChange is one AP).
2. **Leader** `fetchAccessPoliciesBatch` — enrich where source UUIDs mean something.
3. **Follower** `WriteShardData` — resolve **before** tenant adapt + persist.
4. Export `EnrichAPIdentities` wrapper rather than rename ~26 unexported call sites.
5. **Hard-fail / retryable** on enrich or resolve outage — **not** “copy verbatim.”

---

## 3. Impact

- A PC that **joins** the consensus group gets the same identity rewrite as a PC that only receives later ApplyChanges.
- Failed enrich/resolve does not silently store the wrong people (retry instead).
- Group identities on shard copy, not only users (ACP 9 in tavern).

---

## 4. How it was done

1. Grep master for enrich/resolve in shard path — confirmed the gap.
2. Reuse #1535 helpers; add batch-level map; wire fetch + write.
3. Dedicated **worktree** off master (`iam-themis-shard-acp`) so parallel tickets cannot `git switch` the shared tree (lesson from 915519/932537).
4. Six unit tests with fake Enricher/Resolver gRPC servers.
5. Existing `test_lattice_shard_copy.tavern.yaml` already creates ACPs **before** the learner joins (so they travel shard copy). Added ACP 9 (user + **group**). YAML 131 stages parse.
6. Document collision with OPEN [#1607](https://github.com/nutanix-core/iam-themis/pull/1607) (filter then resolve). Not committed pending sequencing (D7).

## 6. Significant technical difficulties

**Bootstrap path ≠ incremental path.** Closing ApplyChange is not closing join. Approach: treat Fetch/Write as a **second producer/consumer pair** that must call the same helpers.

**Verbatim-copy fallback is worse than downtime.** Stale UUIDs persist and look healthy. Approach: **hard-fail** so the copy retries; same posture as #1535.

**PR #1607 edits the same `WriteShardData` block** (selective ACP persistence). Correct order is filter → resolve survivors → adapt → persist. Approach: do not fork a second WriteShardData; pick stack-on-#1607 vs rebase-when-it-lands (D7 open with Manish).

**Tavern cannot prove brownfield rewrite.** Leader and learner share AuthN/Postgres, so UUIDs match and copy is verbatim. Approach: unit tests with **divergent** fake resolver UUIDs; be explicit that tavern is wiring + group-path + no-regression.

**Per-AP vs cross-AP batching.** Up to ~100 Enrich RPCs per page. Approach: keep reviewed per-AP shape (D5) until the perf work Praveen asked on #1535; do not silently change the batching contract.

**Tenant basis on resolve (D4).** Resolve uses received `TenantID` pre-adaptation, mirroring ApplyChange. Cross-PC tenant model needs reviewer confirmation — flagged, not guessed.
