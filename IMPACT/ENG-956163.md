# ENG-956163 — Optimistic concurrency for the role-`products` brownfield migration

**Company impact:** If a Role changes while the products migration is rewriting it, Themis does **not** skip the role or invent a local retry loop. It returns the **typed storage ETag mismatch** on the normal tenant-migration error path. Bootstrap **already** withholds global completion and retries the **entire** failed migration. The next Themis call re-queries the latest ETag and operation list, then recomputes `products`. No API enum/schema change.

## The customer / product problem

Brownfield migration updates Roles that production traffic is also updating. Optimistic concurrency uses ETags. If you retry the **same** storage call with a **captured** expected ETag, it **cannot** succeed.

Wrong implementations:

- Skip the role and continue → that tenant’s products stay wrong, completion may still be recorded.
- Add a Themis-local retry loop on the stale ETag → livelock / wasted work, still wrong.
- Treat mismatch as success → NC thinks products are current.

Right implementation (this ticket):

- Themis: surface the typed conflict.
- Bootstrap: do **not** set completion; retry the **whole** migration operation.
- Next invocation: **re-read** ETag + operations, then recompute.

Do **not** copy this pattern blindly: only valid because **this** coordinator retries the complete operation and withholds completion. If a caller retried a partial operation or could record success anyway, delegating would hide data loss.

## Why this is company-visible

1. **Concurrent IAM admin + upgrade** does not silently drop product tags on some roles.
2. **Completion flag stays honest** — tied to ENG-953364.
3. **OData filters NC relies on** (`products/any(...)`) stay true after brownfield, not only after clean seed.

Related troubleshooting: “retry reports already exists” — first pod may have created state before failing; retries are not automatically isolated. Different bug, same class: **do not confuse error recovery with success.**
