# ENG-956163 — Optimistic concurrency for the role-`products` brownfield migration

Back: [IMPACT index](README.md) · [ENG-932537](ENG-932537.md) · [ENG-953364](ENG-953364.md)  
Canonical: `iam-themis/.notes/PRODUCTS_FIELD_CONTEXT.md` §60

---

## 1. The problem

While the brownfield migration rewrites a Role’s `products`, production traffic can **update the same Role**. Storage uses **ETags**. If Themis retries the **same** update with a **captured** expected ETag, that retry **cannot succeed**.

Wrong recoveries:

- Skip the role and continue → that tenant’s products stay wrong; completion may still be recorded.
- Local retry loop on the stale ETag → livelock.
- Treat mismatch as success → NC thinks products are current.

The coordinator (Bootstrap) **already** withholds global completion and retries the **entire** failed migration. A second retry policy inside Themis would fight that.

---

## 2. How it was solved

Themis-only behavior change — **no new API enum/schema**:

- On ETag mismatch, return the **typed storage conflict** on the normal tenant-migration error path.
- Do **not** skip the role, do **not** add a Themis-local retry loop.
- Bootstrap withholds completion and reruns the migration; the next Themis invocation **re-queries** latest ETag and operation list, then recomputes products.

This is valid **because this coordinator retries the complete operation**. It is not a general “always delegate retries” rule.

---

## 3. Impact

- Concurrent IAM admin + upgrade does not silently drop product tags on some roles.
- Completion (953364) stays coupled to real success.
- OData `products` filters NC relies on remain true after brownfield.

---

## 4. How it was done

1. Identify that the expected ETag is captured on the first attempt — retrying that RPC is a logic error, not a flake.
2. Map the storage conflict onto the existing migration error path.
3. Confirm Bootstrap already retries the whole job.
4. **Go tests** for the internal race; **Tavern** for the black box: create a stale brownfield role → migrate → persist/OData products → **rerun leaves ETag unchanged** (idempotent success).

---

## 5. Technologies and skills

- Optimistic concurrency (ETags), Go race tests (`go test -race` mindset), Tavern black-box, Bootstrap/Themis split of coordinator vs worker.

---

## 6. Significant technical difficulties

**Retrying a captured ETag cannot work.** Approach: fail typed; let the coordinator start a **new** read-modify-write.

**Temptation to add a local loop.** Looks like robustness; duplicates Bootstrap and can hide skip/success bugs. Approach: **one retry owner**.

**Do not generalize.** If a caller retried only a partial operation or could record success anyway, delegating would hide data loss. Approach: document as feature-specific in the IAM notebook next to 953364 and 924709.

Related class (not the same bug): “retry reports already exists” because the first pod created state before failing — retries are not automatically isolated.
