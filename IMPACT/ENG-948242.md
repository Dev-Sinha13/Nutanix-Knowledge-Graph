# ENG-948242 — Backend-driven entity search metadata

**Company impact:** Nutanix Central (and any v4 Entity LIST/GET client) can search IAM entities using **six optional per-attribute search metadata strings**. That is how a global console finds entities by the attributes operators actually type, instead of only by opaque UUIDs. Live **PC verification** confirmed the values round-trip through bootstrap, Postgres JSONB, and iam-proxy.

## The customer / product problem

IAM Entities have a rich attribute document (`object_attribute_list` JSONB). Search UIs need **named metadata** on those attributes (direct, delegated, and a legacy shape that must **omit** metadata). Without a backend contract:

- NC search cannot filter/display attribute search fields consistently.
- Seed config, v1, `/proxy`, and v4 would each invent a different shape.
- `$fv` / swagger version skew (b3 vs b4) would make LIST/GET lie about the schema.

This ticket is **findability** for federated IAM, complementary to `products` (topology) and `authoringScope` (provenance).

---

## What shipped (from the technical-stack record)

- Six optional per-attribute search metadata strings in `objects.json`.
- Persist in the **existing** Object attribute JSONB document (not a new table).
- Expose on **v4 Entity GET and LIST**.
- Nested internal vs public names: `displayName`/`uiDisplayName` internally map to `name`/`displayName` publicly — conversion is required; naive JSON unmarshal puts values in the wrong field.
- **Kronos b4 swagger:** copy `ntnx-api-iam/.../swagger-iam-v4.r1.b4-all.yaml` byte-for-byte into Themis `swagger-iam-v4.1.b4-all.yaml`. Leave released b3 unchanged. Verified with matching SHA-256 plus Themis config/middleware tests.
- Tavern: direct v1, `/proxy`, and v4 seed-config round trips covering **direct, delegated, and legacy** attributes. July 20 follow-up expanded to **14 stages** (`c4e1d16f5`): every write path × all six fields × LIST and GET-by-ID.
