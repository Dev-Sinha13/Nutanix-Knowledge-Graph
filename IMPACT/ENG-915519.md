# ENG-915519 — Global IAM `authoringScope`

Back: [IMPACT index](README.md) · Engineering notes: [inbox index](../inbox/ENG-915519%20-%20Global%20IAM%20authoringScope/00%20-%20Index.md)

---

## 1. The problem

In a federated Nutanix Central deployment, **global** Roles and Access Control Policies are lattice-replicated to every joined Prism Central. The objects look the same on NC and on PC, but they are not the same *kind* of object from an operations point of view: some were authored on NC (the global plane) and some were authored on a PC.

There was **no durable field** that recorded that origin.

Consequences:

- The NC UI could not label “authored on Nutanix Central” vs “authored on this Prism Central.”
- Edit-gating had nothing to key on except `isGlobal`, which is not origin (`isGlobal` says “this replicates,” not “NC created it”).
- A later ownership rule (ENG-949861) could not be specified as “if this row was born on NC, PC must not PUT/DELETE it.”

Non-global (tenant-local) entities do not need this. Only lattice-replicated globals do.

This is **not** the `products` problem (ENG-932537). That field answers *which products the object applies to*. This field answers *who authored it*.

---

## 2. How it was solved

A **read-only, server-stamped, immutable** field `authoringScope` on global Roles and ACPs.

Design locked **2026-06-01** as a **scalar enum** `{NC, PC}` after reviewer pushback against an array:

| Property | Decision |
| --- | --- |
| Who writes | Server only, at create (`ComputeAuthoringScope`) |
| Who reads | Clients; OpenAPI `readOnly` on the enum model so it survives `$ref` |
| Empty | Omitted on the wire (`omitempty`) |
| Updates | SQL UPDATE **omits** the column — immutability in storage, not only in handlers |
| Filters | Equality on `text` + b-tree (not GIN array containment) |

Stamp rules: if `isGlobal` and the cluster is NC → `"NC"`; if PC → `"PC"`; otherwise omit. Clients cannot set it; even if a request body contains it, the server re-stamps.

`omitempty` on the JSON tag is the lattice compatibility story: older peers ignore an unknown field; new peers preserve it. No flag-day on every cluster.

---

## 3. Impact

- **Product:** NC and IAM UIs can show origin. Support can answer “was this created on Central?”
- **Program:** ENG-949861 keys PC-side mutation blocking on `authoringScope == "NC"`. Without this field that ticket has nothing to read.
- **Federation:** origin survives replication without requiring every peer to upgrade first.
- **Correctness:** an entity is authored on **one** product. Shipping an array would have encoded a Kronos design that does not exist (multi-authorship) and made every filter and index harder.

## 4. How it was done

Public IAM fields follow a **three-repo merge train**. Process:

1. **Specify the contract** in one canonical spec (shape, stamp table, omit-on-empty, immutability) so the three PRs cannot drift.
2. **`ntnx-api-iam` first** — OpenAPI: dedicated `authoring_scope.yaml`, `readOnly` on the model, refs from `roles.yaml` and `access_policy.yaml`. PR [#910](https://github.com/nutanix-core/ntnx-api-iam/pull/910).
3. **`iam-utils` second** — internal Swagger + generated Go models. Full `go-swagger` regen was blocked (see difficulties); AuthoringScope-specific portions were **hand-edited to match the intended regen**. PR [#357](https://github.com/nutanix-core/iam-utils/pull/357).
4. **`iam-themis` third** — storage struct, additive Postgres column, INSERT includes the column, UPDATE skips it, all SELECT column lists, handlers call a **single** `ComputeAuthoringScope` from both API and internal converters (defensive re-stamp). PR [#1601](https://github.com/nutanix-core/iam-themis/pull/1601).
5. **Review loop** — 22 comments rolled up and classified (mechanical vs design vs bot). Array→scalar was the design outcome, landed in **one coordinated push across all three PRs** on 2026-06-01 so the wire never mixed array and scalar in flight.
6. **Verification ladder** — `gofmt -l` → `go build -mod=vendor` → `go vet` (new warnings only vs master) → `go test -mod=vendor -count=1` → re-verify **after rebase**.
7. **Durable memory** — `ntnx-api-iam/.notes/AUTHORING_SCOPE_CONTEXT.md` plus vault indexes. Decision log kept **separate** from open questions so later sessions did not re-litigate scalar vs array.

Merge order is strict: schema → utils → Themis. Themis cannot copy the field from vendored request models until #910/#357 land; until then Themis stamps locally and leaves a revendor follow-up.

## 6. Significant technical difficulties

**Array vs scalar (design, not a nit).** Early framing used `[]string` “for forward-extensibility.” Aditya (#910) and Praveen (#1601) pushed back: an entity is authored on exactly one product; equality filters and a b-tree beat GIN containment. Approach: treat it as a **locked contract change**, convert all three PRs together, document that multi-origin if it ever appears is a **new** field (`replicatedFrom`), not an overloaded `authoringScope`. Handler snippets in older notes still show `[]string` — the locked spec is scalar.

**Reads returned empty after a “done” migration.** INSERT and migration were correct; **five SELECT column-list constants** never included `authoring_scope`. Symptom: column exists in Postgres, GET returns blank. Approach: after any new column, grep every `*AllColumns*` / scan switch, not only migrate.go.

**`go-swagger` version pin (Manish).** Full iam-utils regeneration was blocked. Approach: hand-edit only the AuthoringScope-shaped portions to mirror intended regen (`AccessPolicyType` / `OperationSchemaChangeImpact` precedents); record that a later regen must match; do not pretend the pin is gone.

**Parallel agents on one Themis checkout.** `git switch` from another session moved HEAD mid-work; `go.mod` `replace => ../sibling` from ENG-932537 made `go build -mod=vendor` **silently rewrite vendor/** with mixed fields from the other ticket. Approach: `git rev-parse --abbrev-ref HEAD` at the start of every git/build chain; later tickets moved to **worktrees**. Local replace + vendor mode is treated as contamination, not as a convenience.

**ntnx-api-iam Maven Python SDK vs pyenv.** `mvn install` failed in `generate_rst` because Homebrew Python 3.14 was on `PATH` while the module needed pyenv 3.9; a leftover `.venv` was poisoned. Approach: wipe the generated venv, prepend pyenv shims. Schema-review Maven plugin goals had also been renamed (`review`/`swaggerFile` → `generate-report`/`inputOpenApiFile`) — inspect current `help:describe`, do not copy stale pom snippets.
