# Decisions Log

- **D1 — Allow-set, not deny-list.** Permit only known externally-managed types on a global ACP: users `{SAML, LDAP, EXTERNAL, PROPAGATED}`, groups `{SAML, LDAP, PROPAGATED}`. Everything else — `LOCAL`, `SERVICE_ACCOUNT`, `UNKNOWN`, `REDACTED`, and a nil type — is rejected. Rationale: it satisfies the ticket's explicit "reject LOCAL + SA" and is fail-closed for ambiguous/unknown types, which is the right posture for a data-integrity guardrail. `EXTERNAL` (gmail-style, not in tenant IDP) and `PROPAGATED` (synced from NC) are treated as externally-managed. Trivially flippable to a pure deny-list by changing the two allow-set maps.
- **D2 — Validation source = `IAMAuthn` SDK `GetUserById`/`GetUserGroupById`.** Mirrors the existing, reviewed pattern in `v4_role_membership_validator.go` (same client, same 404 handling, same `mapIAMAuthnSDKError`). Rejected alternative: reuse the `connectorType` produced by `enrichAPIdentities` (gRPC IdentityEnricher) — it runs adjacent, but its connector semantics are less explicit than `userType`/`groupType`, and enrichment happens *after* the point we want to fail fast. Chose the explicit type lookup for clarity + pattern reuse.
- **D3 — Insertion point after `CheckIfGlobalChangeAllowed`, before enrich/propose** (v4 create ~L891, v4 update ~L431). Consequence: gating is inherent — the validator only runs for global ACPs on an NC cluster with global sync enabled. No new feature flag needed (satisfies "gate behind the primary Lattice/Global-IAM flag").
- **D4 — Wildcard `*` entries skipped.** `processUserFilter` puts `uuid`/`*` operands into `UserList` and `group` operands into `UserGroupList`; `enrichAPIdentities` already skips `*`. A `*` is a dynamic "match any" filter, not a concrete local identity, so we skip it (consistent with "purely dynamic filters rely on runtime"). Documented as a known gap: a global ACP with `user:*` is not rejected.
- **D5 — v4 scope only.** The v1 / proxy `serveAccessPolicyPOST`/`PUT` (`access_policy.go`) persist locally and do **not** propose to the lattice or gate on global sync; global ACP authoring is a v4 concern. Not wiring the guardrail into v1 to keep scope tight. Flagged as a follow-up in [[04 - Open Questions & Status]] if v1 global creation turns out to be a real path.
- **D6 — Update conversion already blocked.** `v4_access_policy.go` rejects flipping an ACP between global and local (existing `existingAcp.IsGlobal != requestIsGlobal` check). So on update we validate only when the (unchanged) `isGlobal` is true; no need to handle a local→global transition.
- **D7 — Error surface = `util.RequestValidationError`** with a message naming the offending identity + its resolved type. Consistent with how the membership validator reports identity validation failures; avoids adding a new code to the vendored `errorcodes` package.
- **D8 — Dedicated worktree** `/.wt-themis-global-acp` off `origin/master`, branch `ENG-910350-global-acp-external-identity` — same practice as the sibling tickets (avoids disturbing the shared checkout, which was on `ENG-910347-shard-acp-resolver`).
